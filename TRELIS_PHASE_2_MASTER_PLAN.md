## PART 2: WHAT FOOD DIVERSITY ACTUALLY IS (Since You Asked)

Your GP's playbook emphasizes gut microbiome restoration. The single most validated intervention for gut diversity is eating a wide variety of plant foods. A landmark study (the American Gut Project) found that people who ate 30+ different plant species per week had significantly more diverse gut microbiomes than those who ate fewer than 10.

"Plant species" means: every different fruit, vegetable, grain, legume, nut, seed, herb, and spice counts as one. So if you eat rice, dal, tomato, onion, garlic, coriander, cumin, turmeric, banana, and spinach in one day — that's 10 plant sources from a single Indian meal.

The 30/week target is surprisingly achievable with Indian food because Indian cooking uses many spices and ingredients per dish. The counter in your app gamifies this — each time you eat something new this week, tap +1. The progress bar fills toward 30.

**Why the app failed to communicate this:** There's no onboarding explanation, no tooltip, no "why this matters" anywhere. In Phase 2, every widget needs a one-line "why" that's visible on first use and hideable after.

### The Concept

Your logo should be the **Lattice Ring** — a fusion of two things:

1. **The Pulse Ring** (your app's most recognizable UI element — the animated circle that fills as your day progresses)
2. **The Trellis Lattice** (the crisscross support structure that gives the brand its name)

At app-icon size (small, on phone home screen), it reads as a clean, partially-filled circle — immediately associated with "progress" and "daily health." At larger sizes (splash screen, website, marketing), the subtle lattice texture within the ring's stroke becomes visible — revealing the trellis.

The gap in the ring (at the top-right, about 30 degrees) represents two things: the day is not yet complete (there's always room to grow), and the opening where the vine enters the trellis structure.

### TRACK A — THE SYNC ENGINE

This is what Gemini flagged as Phase 2 Step 1. It bridges your local Zustand data to Supabase cloud.

**What it does:** When authenticated, every action (anchor toggle, supplement check, gut log, etc.) optimistically updates local state THEN pushes to Supabase. When app opens, it pulls latest from Supabase and merges with local state (local wins on conflict for offline-first).

**Priority:** HIGH. Without this, all your data lives only on your device. Phone reset = everything gone.

**Gemini prompt for this:**

```
PHASE 2 — TRACK A: SYNC ENGINE

Build a bidirectional sync layer between the Zustand store 
and Supabase. Rules:

1. OPTIMISTIC LOCAL-FIRST: Every user action updates Zustand 
   instantly. Then async pushes to Supabase. UI never waits 
   for network.

2. ON APP OPEN: Check auth session. If authenticated, pull 
   latest from Supabase for today's date. Merge strategy: 
   if local has data that Supabase doesn't, push local up. 
   If Supabase has data local doesn't, pull down. If both 
   have data, local wins (user's device is truth).

3. SYNC THESE ENTITIES:
   - daily_rituals: upsert on morning check-in complete 
     and evening check-in complete (keyed on user_id + date)
   - user_anchors: sync full array on any add/remove/edit
   - anchor_logs: upsert on toggle (keyed on user_id + 
     anchor_id + date)
   - user_supplements: sync full array on any add/remove
   - supplement_logs: upsert on toggle
   - user_vision: upsert on edit
   - notes_of_life: push new notes, pull existing on load
   - weekly_stats: upsert weekly_plant_count

4. SYNC STATUS INDICATOR: Add a tiny dot in the header — 
   green = synced, amber = pending, hidden when offline.
   Never block UI for sync status.

5. ERROR HANDLING: If Supabase push fails (network), queue 
   it locally. Retry on next app open or next successful push.

6. DO NOT modify any UI components, design tokens, or the 
   daily behavioral loop. This is backend-only work.
```

#### C2. Android App via Capacitor

**Current URL (localhost:3000) vs Android App:**
Your current dev URL is a web app running locally. The Android app is the SAME code wrapped in Capacitor's native container. The difference:

```
WEB APP (PWA):
- Accessed via browser URL (trelislife.app)
- Can be "installed" on home screen via browser prompt
- Limited native access (no haptics, no push notifications)
- Works on any device with a browser

ANDROID APP (Capacitor):
- Downloaded from Play Store (or sideloaded APK)
- Full native access (haptics, push notifications, biometrics)
- Runs in its own app container (not in browser)
- Feels like a "real" native app
- Same codebase — just wrapped differently

HOW TO BUILD IT:
npx cap sync        // copies your built web app into android/
npx cap open android // opens Android Studio
// In Android Studio: Build → Generate Signed Bundle → .aab file
// Upload .aab to Google Play Console
```

**Phase 2 target:** Get the Capacitor Android build working and tested on your physical phone. You don't need to publish to Play Store yet — sideloading the APK for personal testing is fine.
